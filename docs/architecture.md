# Architecture

The long Tech Stack notes, moved out of `CLAUDE.md` so they do not load on every turn. Read the bullet for the area you change.

## Tech Stack

- **Framework:** Astro 7, `output: "static"`, `build.format: "file"`, prerendered to `dist/` (`astro.config.mjs`; React 19 islands through `@astrojs/react`; Tailwind v4 through `@tailwindcss/vite`). `build.format: "file"` writes `/blog` as `dist/blog.html` and `/blog/<slug>` as `dist/blog/<slug>.html`; Cloudflare serves them without the `.html` suffix. Routes: `/` (`src/pages/index.astro`, layout `src/layouts/Base.astro`), 404 (`src/pages/404.astro` → `dist/404.html`, `noindex`), `/sitemap.xml` (`src/pages/sitemap.xml.ts`, with image entries; `lastmod` is the CV feed's `updatedAt`, the time the résumé was last saved, never the build time), `/robots.txt`, `/manifest.webmanifest` (`src/pages/manifest.webmanifest.ts`), `/llms.txt` (`src/pages/llms.txt.ts`), `/cv.json` (`src/pages/cv.json.ts`), `/resume.pdf` (`src/pages/resume.pdf.ts`), and the blog: `/blog`, `/blog/<slug>`, `/blog/feed.xml`, `/blog/feed.json` and `/blog/<slug>.md` (see **Blog** below; the sitemap's blog entries use the post dates, not the CV feed's). The home page, `/sitemap.xml`, `/llms.txt`, `/cv.json` and `/resume.pdf` are built from `personal.ts`, `products.ts`, `i18n.ts`, the build-time repo list and the CV feed. The home page stays one card; the only other pages are the blog and the 404.
- **Dev:** `devToolbar: { enabled: false }` in `astro.config.mjs`, so `astro dev` shows no Astro toolbar. `pnpm dev` runs the CV fetch and the blog prebuild with drafts, then `astro dev --port 4321`.
- **UI:** Tailwind v4 (`@theme inline` + `@utility`, via `@tailwindcss/vite`). `globals.css` starts with `@import "tailwindcss" source(none)` and `@source "../"`, so Tailwind scans only `src/` and never `.agents/`, `dist/` or old worktrees. `postcss.config.mjs` (plain ESM, not run through Node's type stripping, so it stays `.mjs`) holds only `scripts/postcss-color-mix.mjs`, which Vite runs on the CSS after the Tailwind plugin has produced it: Tailwind puts each `color-mix()` rule in a `@supports (color: color-mix(in lab, red, red))` block after a fallback rule; the plugin drops the fallback declarations and unwraps the block, so every browser gets the `color-mix()` value and a browser without `color-mix()` (Chrome before 111, Safari before 16.2) loses those colors. ESLint ignores the `.mjs` config files (the typed rules need type information they cannot give). Astro components render to HTML at build time and ship no JavaScript; only React islands (hydrated with a `client:` directive) run in the browser: the sky (`space-background.tsx`), the PDF button, the portrait dialog, the planets (`repo-planets-canvas.tsx` → `src/lib/repo-planets.ts`, one raw WebGL2 canvas that draws the repo planets and the logo planets from `src/lib/logo-planet.ts` and `src/lib/logo-motion.ts`, with the matrices, sphere and ring geometry, color conversion and program helpers in `src/lib/planet-gl.ts`; no three.js), the pause button (`motion-toggle.tsx`), the privacy OK button (`privacy-ack.tsx`), the Vienna globe launcher (`city-globe-launcher.tsx`, which imports `city-globe-stage.tsx` → `src/lib/city-globe.ts` only on click) and `effects-init.tsx`.
- **Globe data:** `src/lib/globe-data.ts` (coastlines, Austria, borders) is generated by `scripts/generate-globe-data.ts` from Natural Earth through `world-atlas`: run `pnpm add -D world-atlas`, `node scripts/generate-globe-data.ts`, then `pnpm remove world-atlas`. It is loaded only after a click on "Show on the globe". Nothing is fetched at run time.
- **Fonts:** self-hosted woff2 in `public/fonts/` with versioned names (Inter Variable latin, Geist Mono 400/500 latin, Geist at a fixed weight 600 for the name only (chosen by the owner on 2026-10-12 in the "Name Font Picker" artifact: 47/44 of the display size, letter spacing 0.02em; Parkinsans before), plus small `*-extra-*` files for ć č đ š ž, cut with fonttools' `pyftsubset` from `~/powertools/py/bin` and woff2 output). The profile header SVG embeds Inter and Geist. `@font-face` sits at the top of `globals.css`. Metric-matched `local()` fallback faces (`Inter Fallback` on Arial in four weight bands, `Geist Fallback` on Arial Bold, `Geist Mono Fallback` on Courier New, each with `size-adjust` and `ascent-override`, `descent-override`, `line-gap-override`, measured against the real fonts on 2026-10-12) sit right after each font in the stacks, so the swap moves nothing (mobile CLS 0.14 to 0.0007 on Lighthouse with devtools throttling); re-measure them when a font file changes. Do not preload them: it pushed LCP from 0.9 s to 1.5 s on slow 4G. To change a font, ship a new file name (the `/fonts/*` cache rule is immutable).
- **Icons:** `<Icon>` (`src/components/icon.tsx`) renders inline SVG from `src/lib/icon-data.ts`. Sets in use: `circle-flags`, `lucide`, `simple-icons`. A new `set:name` needs `pnpm icons` (run `pnpm add -D @iconify-json/<set>` for each set first, then remove them again).
- **GitHub data:** `src/lib/github.ts` runs at build time. `getRepos` picks the repos and adds every language at 3% or more with its GitHub Linguist color (one GraphQL `repository.languages` query per repo; colors are validated as `#rrggbb` and dropped otherwise). `getContact` reads the public email and the LinkedIn social account from the GitHub profile; `personal.ts` holds neither. `GITHUB_TOKEN` is **required**: GitHub shows a profile email only to authenticated requests. Set it as a Cloudflare build variable. Locally, when it is unset, `github.ts` asks `gh auth token` at run time, so `pnpm dev`, `pnpm build` and the pre-commit hook work without a token file (nothing is written to disk). Any non-200 answer, a missing email or a missing LinkedIn fails the build on purpose. `getProject(login, repo)` (built for project pages, no page uses it yet) returns the default branch, the README rendered by GitHub's `/markdown` endpoint (GFM, repo context) and the last published releases (`per_page=5`, drafts and prereleases dropped, assets kept). `src/lib/readme-html.ts` (`sanitizeReadme`, `sanitize-html`) cleans that HTML: resolves relative links (GitHub blob URLs) and images (raw.githubusercontent.com) against the repo and branch, rejects `..` paths, keeps only http(s) and mailto, opens web links with `noopener noreferrer`, keeps images only from GitHub image hosts, drops badges (shields.io, badge.fury.io), the first `h1`, landmark tags, non-checkbox inputs and links left empty, and keeps links around nested images. Both are covered only by tests so far.
- **CV feed:** `scripts/cv-fetch.ts` runs before `astro build` (`pnpm build`, `pnpm dev` and `pnpm check` all start with it; `pnpm dev` fetches once at start) and asks the jobsearch app (hirista) for `GET {CV_FEED_URL}/api/public/cv` with `Authorization: Bearer {CV_FEED_TOKEN}`, a 20 s timeout and `redirect: "error"`. `CV_FEED_URL` is the origin `https://hirista.app` (the old `js.stevanpavlovic.com` host was removed on 2026-10-12); a URL that is not https fails before any request, except `http:` on `127.0.0.1`, `localhost` and `[::1]` for tests. The script writes the parsed résumé, with `basics.phone` blanked (`stripPrivate`), to the gitignored `.cv/cv.json` and the source (`feed` or `live`) to `.cv/source`; `getCv()` in `src/lib/cv.ts` only reads that file (once per process), so every page, route and the PDF show one version. **Fallback:** only a 20 s timeout, a network error or a 5xx makes the script use the live `https://stevanpavlovic.com/cv.json` (source `live`, a warning in the log). A 404 (the feed answers 404 with an empty body to every refusal: no or wrong token, wrong method, no résumé saved), any other non-200, a redirect, a missing or non-https variable, bad JSON or a schema failure fails the build and never falls back. **Guard:** `scripts/cv-guard.ts` runs after `astro build` and fails the build when the feed's `updatedAt` is newer than the built data (a résumé saved during the build; a newer build is on its way). It is skipped after a `live` fallback or when the feed does not answer. Both scripts load `.env.local` when it exists; `process.env` wins. `cvSchema` mirrors jobsearch's `resumeDataSchema` (`src/cvexp/types.ts` there): `basics`, `summary`, `experience`, `education`, `skills`, `languages`, `projects` (http(s) links only), every field defaulted, plus `updatedAt` (ISO); there is no `cvexp` dependency, as the npm package lacks `projects`. `src/lib/cv-feed.fixture.json` is a byte copy of hirista's `fixtures/cv-feed.json` and `src/lib/cv-contract.test.ts` parses it with `cvSchema`; `.prettierignore` keeps it byte-exact. Change a feed shape in both repos in the same session. Both variables are **required**: Cloudflare build variables, GitHub Actions secrets (`ci.yml`) and Dependabot secrets, locally `~/work/website/.env.local` (gitignored, holds `CV_FEED_URL` and `CV_FEED_TOKEN`). Never print the token; no error message holds it or the URL. Saving a résumé in hirista fires this site's Workers Builds deploy hook. The integration contract and the secrets matrix live in the hirista repo's `DEPLOYMENT.md`, section "Integration contract: hirista.app ⇄ stevanpavlovic.com" (a private repo, so no link). `src/pages/cv.json.ts` serves the result as `/cv.json`; `src/lib/cv-llms.ts` adds Experience, Skills, Education and, when there are any, the résumé's projects to `llms.txt`.
- **Static files:** there is no committed PDF. `/resume.pdf` is a static endpoint (`src/pages/resume.pdf.ts`, prerendered): `src/lib/resume-file.ts` renders the feed's résumé once per build with `@react-pdf/renderer` (`src/lib/resume-pdf.ts`, a port of cvexp's layout; Inter from `@fontsource/inter`; colors in `theme.ts`) and reads the photo from `public/` when `basics.pictureUrl` is on the site's own origin (`public/stevan-pavlovic.jpeg` backs the feed's `pictureUrl`). The button downloads it as `Stevan_Pavlovic_Resume.pdf`. Portraits (`public/portraits/`) and favicons are committed. `og-image.jpg` (1200x630: the night sky, the portrait, name, title, Vienna) and `linkedin-cover.png` (1584x396, no text, chosen by the owner on 2026-10-12 from six prototypes: the night sky with stars, the low clouds, one shooting star over the middle and soft light rays fanning in from the top-left corner, which come from the corona centered off-canvas with `coronaSize` and `coronaBright` raised in a patched copy of the shader (`longRaysShader` in `src/lib/sky-rays.ts`, shared with the post header: `coronaSize` 1.6, `coronaBright` 1.3; the site's home shader stays as tuned, and `patchShader` fails when one of those lines changes in `sky-shader.ts`; the generator also takes `cornerCorona(396)` and `cornerMeteor` from there); the ray source and the shooting star stay clear of the LinkedIn photo in the lower left and of the 117 px the phone app crops on each side; served at `/linkedin-cover.png` so the owner can download the latest and upload it to LinkedIn by hand, as no LinkedIn API lets a self-serve app change a personal profile's background; text kept in x 620 to 1440, y 60 to 300, clear of the profile photo) are generated by `scripts/generate-images.ts`: it draws one frame of the real sky shader (`src/lib/sky-shader.ts`) with fixed uniforms in headless system Chrome on SwiftShader (`playwright-core`, `channel: "chrome"`), lays the text from `personal.ts`, `i18n.ts`, `theme.ts`, `icon-data.ts` and the `@font-face` fonts on top and writes a file only when its bytes change (about 6 s). `.github/workflows/images.yml` runs it on a push that touches those inputs (or by hand), commits changed images as `github-actions[bot]` and pushes, which deploys; a failure opens one `images-sync` issue and the next good run closes it. The images are deterministic script output, not AI output: one shader frame from fixed uniforms (no clock, no random), and the PNG holds only `IHDR`, `IDAT` and `IEND` (no metadata or content credentials). The script renders each image twice and fails when the bytes differ; runs on the same platform give identical bytes, while a Mac and the Linux runner differ by at most 6 of 255 in about 0.4% of the channels, so only CI writes the committed files. Cloudflare builds copy the committed files and never render them, so every deploy ships the same bytes. Never edit either image by hand or commit a local render: change the inputs or the script. Both are committed. The only files in `public/` written at build time are the blog's (`public/blog-media/`, `public/blog/` and `public/build.json`, all gitignored, written by `scripts/blog-build.ts`; see **Blog**). `src/lib/resume-facts.ts` only reads the page count (page tree `/Count`, also inside Flate object streams, else `/Type /Page` objects) and the size in KB from the generated PDF for the PDF tooltip, and fails the build when it finds no page count. `cv.json` is not committed: it comes from the CV feed at build time (see above).
- **Content:** `src/lib/personal.ts` (name, title, summary, city, website, GitHub); email and LinkedIn come from GitHub (see above); all UI strings in `src/lib/i18n.ts`.
- **Products:** `src/lib/products.ts` is hand-written on purpose (the CV feed's `projects` have no role, logo, color or category, and a résumé edit must not reshape the card): `key`, `name`, `url`, `schemaType` (`WebApplication` for hirista, `SoftwareApplication` for Safety Real Time) and `applicationCategory`, with `role`, `period` and `line` from `en.products.items[key]` and the colors (`disc`, `mark`, `accent`, `tint`) from `productPalette` in `theme.ts`. `src/lib/product-marks.ts` holds the mark path data (`viewBox`, a `transform`, layers with `ink` `mark` or `accent`); the Safety Real Time mark is the six paths of `https://safetyrealtime.com/wp-content/uploads/2022/11/srt_logo.svg`, navy on green after the brand's favicon. They feed the product tiles, the JSON-LD (`WebApplication`/`SoftwareApplication` with the person as `creator`), the `llms.txt` "Products" section (`productLlmsLines`, after the open-source projects; `isProductUrl` drops a résumé project whose host is a product's, so hirista is listed once), the `/mcp` `products` tool and the profile README. Both files use relative `./x.ts` imports, so `node --test` and `src/profile/cli.ts` load them. The tile period is hand-written while the fleet popover reads its own from the feed; if they drift, take the tile's from the feed.
- **Pkg mgr:** pnpm 12 (`packageManager`), Node 24 (`.nvmrc`), both enforced by `engines` with `engineStrict`. All pnpm settings live in `pnpm-workspace.yaml`: the build-script allowlist (`allowBuilds`, `strictDepBuilds`), a one-day `minimumReleaseAge`, `trustPolicy: no-downgrade` with one exact `trustPolicyExclude` entry (`semver@6.3.1`, a 2023 security backport without provenance; evidence in the commit that added it), `blockExoticSubdeps` and `verifyDepsBeforeRun: install` (scripts install first when the lockfile changed). Keep `package.json` scripts to the eight that exist (`build`, `check`, `dev`, `fix`, `icons`, `prepare`, `preview`, `profile:build`). Add a trust exception only as an exact `name@version` with checked evidence, never by turning the policy off.
- **Profile mirror:** `src/profile/` builds the README and images for `pavstev/pavstev` from `personal.ts`, `products.ts`, `i18n.ts`, `icon-data.ts`, `theme.ts`, `template.ts` and the same `getRepos` call as the site. The README lists the repos, then a "## 2 products" section (links only, left out when the list is empty; the product links must be https but are never fetched, as external hosts would make `pnpm check` flaky). `render.ts` is pure (data in, `{ path, contents }[]` out, deterministic); `cli.ts` is the only file that reads or writes. Output goes to the gitignored `.profile-out/`. `.github/workflows/profile.yml` pushes it to `pavstev/pavstev` with the deploy key secret `PROFILE_DEPLOY_KEY`, on a push that touches its inputs (the `paths` list must hold every file `src/profile/` imports, `products.ts` included) and daily. A failed run on `main` opens one issue labelled `profile-sync` (later failures comment on it) and the next good run closes it; scheduled runs also call the workflow `enable` API, so 60 days without commits do not switch the schedule off (`issues: write` and `actions: write` at job level only). The code never reaches the site bundle (nothing in `src/pages`, `src/layouts` or `src/components` imports it). The header is a 2400x360 SVG: the name and title in embedded Inter and Geist over `src/profile/header-sky.webp`, the blog's night sky with the corner rays (the `linkedin-cover.png` look, about 19 KB). `scripts/generate-images.ts` renders that WebP, and `images.yml` commits it and starts `profile.yml`, since a push by the workflow token starts no other workflow. Keep the SVG under 120 KB (about 108 KB now).
- **LinkedIn sync:** no allowed API can change a personal LinkedIn profile (`.agents/linkedin-cover-automation-report.md`), so LinkedIn stays a manual copy of this site and GitHub tells the owner what to change. `src/lib/linkedin-fields.ts` (pure, tested) builds a deterministic snapshot of every field that also lives on LinkedIn (the sha256 of `public/linkedin-cover.png` and of the portrait files, name, headline, location, website, About from `personal.ts`, experience, education, skills, languages and projects from the live `/cv.json`, Featured from `products.ts`; never `basics.phone`) and diffs two snapshots. `scripts/linkedin-sync.ts` fetches the public `https://stevanpavlovic.com/cv.json` (no token), reads the last snapshot from `--previous` and writes `status` (`first`, `changed` or `same`), `title.txt`, `body.md` and `state.md` to `--out`; `--dry-run` prints and writes nothing. `.github/workflows/linkedin-sync.yml` runs on a push that touches those sources, daily (the live file is the truth for résumé edits made in hirista) and by hand. State lives in one closed, locked issue labelled `linkedin-state` (never in the repo, as a commit redeploys the site). A change opens `Update LinkedIn: <places>` labelled `linkedin-sync` that mentions the owner, or comments on the open one; the first run opens one checklist of every field. Keep `linkedin-sync.yml`'s `paths` equal to the files the script reads. Phase 2 (reading LinkedIn through the EU DMA Member Data Portability API for a real match check) is not built; it needs a LinkedIn developer app, OAuth and a GitHub secret from the owner.
- **Worker:** `worker/index.ts` is `main` in `wrangler.jsonc` (`nodejs_compat`). `assets.run_worker_first` is `["/mcp", "/mcp/*"]`, so only those paths reach it; every other path is served straight from `dist`. It routes `/mcp` and `/mcp/*` to `mcp.ts` and passes anything else to `env.ASSETS`. There is no Ask panel and no `/api` route: the owner removed them, with their human check and AI binding, on 2026-10-08; do not add either back without a new decision. Bindings: `MCP_LIMITER` (rate limit, 20 per 60 s, keyed by `CF-Connecting-IP`; namespace `2001`; a namespace id is any integer you pick, unique per account, and needs no dashboard step) and `ASSETS`. `worker-configuration.d.ts` is generated by `CLOUDFLARE_LOAD_DEV_VARS_FROM_DOT_ENV=false pnpm exec wrangler types` (rerun after any binding change; without the variable wrangler copies the names in `.env.local` into the file), committed, and excluded from Prettier, ESLint and the root `tsconfig.json`; `worker/tsconfig.json` extends the root one and includes it. Errors are JSON `{ "error": code }` with `Cache-Control: no-store`. Every `/mcp` answer carries `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy` and `Permissions-Policy` (`withSecurityHeaders` in `worker/http.ts`, the same values as the `/*` rule in `public/_headers`; no CSP, as the bodies are JSON or an event stream). Keep the two lists equal. `public/_headers` also sets `Content-Type` with `charset=utf-8` on `/llms.txt` and `/cv.json`, as both hold non-ASCII text. `facts.ts` reads `/cv.json` (zod schema, `projects` included) and `/llms.txt` from `ASSETS`, caches the promise per origin and drops it on failure, and holds the text helpers `/mcp` uses. `wrangler.jsonc` has `workers_dev: false` and `preview_urls: false`: the Worker answers on the custom domain only (see **No previews**).
- **No weather (owner call 2026-10-14):** the home sky has no live data. The `/weather` Worker route, the Open-Meteo fetch, the footer credit and the rain, snow, fog and storm looks were removed with the move to the 100 km view; the Earth keeps one partly cloudy look (`earthClouds` in `src/lib/sky-preset.ts`) and the blog sky keeps its clear one (`blogLook`). `?at=<ISO instant>` still pins the time and also marks the page as a real browser, so a headless test run gets the live sky instead of the crawler night. Do not add a data source back without a new decision: the site then needs a visible credit next to it.
- **`/mcp`:** a stateless MCP server (`@modelcontextprotocol/sdk`, `WebStandardStreamableHTTPServerTransport`, 16 KB body cap), built per request after the rate limit; `POST` only. Eight read-only tools: `profile`, `experience`, `skills` (from `cv.json`), `projects`, `products` and `contact` take no input; `posts` and `post` belong to the blog (see **Blog**); `post` answers a slug it does not list, or one whose Markdown copy is missing, with `{"error":"not_found"}` as a tool error (`isError: true`). `projects` lists the "Open-source projects" section of `llms.txt`, then the résumé's projects from `cv.json` (so hirista can show up in `projects` and `products`, by choice); `products` is the "Products" section of `llms.txt` ("Not available." when it is missing); `contact` is the "Links" section. ESLint's `import-x/no-unresolved` ignores the SDK's subpath imports in `worker/`.
- **Blog:** MDX posts in `content/blog/<slug>/index.mdx`, one folder per post (slug: lowercase letters and digits in groups joined by single dashes, at most 80 characters; `isSlug` in `src/lib/blog/slug.ts` is the one check, used by `posts.ts`, `chart-data.ts` and the Worker). How to add a post: `.claude/rules/blog.md`.
  - **Content model:** `src/lib/blog/schema.ts` holds the zod `strictObject` frontmatter (an unknown key fails the build): `title`, `description` (at most 160 characters), `date`, optional `updated`, `draft` (default false), `tags` (1 to 5). `posts.ts` reads the folder (`listPosts`, `findPost`; reading time from `reading.ts`) and fails with `content/blog/<slug>/index.mdx: <field>: <message>`.
  - **Render:** the post page calls `evaluate()` from `@mdx-js/mdx` (`src/lib/blog/render.tsx`, `react/jsx-runtime`; no compile step). Plugins: remark-gfm, rehype-slug, `rehypeHeadingAnchors`, `@shikijs/rehype` (the `createCssVariablesTheme` theme, token colors in `globals.css`) and `rehypeToc` (h2 and h3 into `file.data.toc`; see **Blog chrome** for the rail, the tree lines and the drawer). The component map: `a` to `BlogLink`, `img` to `BlogImage`, plus `Figure`, `Note`, `Chart` and `Diagram`. Post pages ship client JS only for the sky, the bar spy, the TOC spy and drawer, and `PostEffects` (`post-effects.tsx`: it marks each `<img>` in a `<picture>` as loaded, which drops the blur, and wires the image zoom).
  - **Plain converter:** `src/lib/blog/plain.ts` (`toMarkdown`, `toFeedHtml`; Node-safe: no JSX, no `@/` imports) parses with remark-parse, remark-mdx and remark-gfm (one `parseMdx` in `src/lib/blog/mdx-tree.ts`, shared with the image finder in `media.ts` and cached by body, so a post is parsed once per build) and splices the original source by node offsets, so prose, code and footnotes stay byte-exact. Only JSX, MDX expressions, ESM and relative images change: `Note` becomes a blockquote, `Figure` an absolute image plus an italic caption, `Chart` its caption plus the `chartLines` list, `Diagram` its caption plus `diagramText`. `toFeedHtml` continues through rehype (no raw HTML) and makes every `href` and `src` absolute.
  - **Prebuild:** `scripts/blog-build.ts` runs in `pnpm build` and `pnpm dev` after `cv-fetch` (`pnpm build` first exports one instant as `BLOG_BUILT_AT`; the prebuild picks posts at that instant, writes it as `builtAt` to `public/build.json`, and `astro build` reads it through `builtInstant()` as the default `now`, so all three agree; its work is the exported `buildBlog({ drafts, now, root })`, so `scripts/blog-build.test.ts` can run it on a temp directory and check that a draft gets no Markdown copy, share image or manifest entry in a production build). It reads the posts (drafts only when `showDrafts()`), finds every local image a post references (`Figure src`, `img`, Markdown images; a missing file fails the build with `image "<file>" not found`), and writes AVIF (quality 60) and WebP (quality 82) at 480, 768 and 1344 px wide (never upscaled) plus a 16 px blur to `public/blog-media/<slug>/<name>.<sha256 of the encoded bytes, 8 hex>.<width>.<ext>`. It draws a 1200x630 share PNG per post with `satori` (rendered to PNG with `sharp`; the post's `cover.*` resized as the background, else the page background; title in Inter 600, with Inter `latin-ext` loaded as a second family "Inter Ext" so `satori` never fetches a font; `share.test.ts` asserts no request goes out). It writes `.blog/media.json` (the manifest `src/lib/blog/media.ts` reads; `mediaPath` returns the hashed name when the manifest has the image), the Markdown copies `public/blog/<slug>.md` and `public/build.json` (`{"sha","builtAt"}`; the sha is `WORKERS_CI_COMMIT_SHA` or `git rev-parse HEAD` and must be 40 hex). A file is written only when its bytes differ, and stale files are pruned. All four outputs are gitignored (`.blog/`, `public/blog-media/`, `public/blog/`, `public/build.json`), and ESLint and Prettier skip the generated Markdown. Only referenced images ship: an unused still or a `cover.webp` stays in `content/blog/`. Satori cannot read WebP, so the share image converts the cover with sharp first. After `astro build`, `scripts/preload-guard.ts` reads every `dist/blog/*.html` and fails the build when a post page holds a `<link rel="preload" as="image">` (`imagePreloads` is the pure check, tested on HTML strings); `/` keeps its portrait preload; `/blog` has no portrait any more. `public/_headers` has a block for each output: `/blog-media/*` immutable, `/blog/*.md` as `text/markdown; charset=utf-8`, `/build.json` `no-store`, both feeds with their own types, all detaching the CSP.
